## 1. 成本结构

### 1.1 外部 API（现金支出，与用户数线性相关）

MiMo-V2.6-Flash 国内价（元 / 百万 tokens）：

| | 缓存命中 | 未命中 | 输出 |
|---|---|---|---|
| 输入 | 0.02 | 1.00 | — |
| 输出 | — | — | 2.00 |

单个 Plus 用户用满 20 万 token/月（输入 80% / 输出 20%）：

| 项 | 计算 | 成本 |
|---|---|---|
| 输入未命中 | 160,000 ÷ 1e6 × ¥1 | ¥0.16 |
| 输出 | 40,000 ÷ 1e6 × ¥2 | ¥0.08 |
| **合计** | | **¥0.24 / 月** |

### 1.2 CloudBase（资源点制，1,000 点 = ¥1）

套餐：**个人版 ¥19.9/月 = 40,000 点**（固定支出，与用户数无关）。超出部分按量付费。

计费换算：`资源点 = 0.11108 点 / GBs`，其中 `1 GBs = 1GB 内存运行 1 秒`。

按「100 个活跃 Plus 用户」估算（月）：

| 资源 | 单价 | 用量 | 资源点 |
|---|---|---|---|
| 云函数资源使用量（AI） | 0.11108 点/GBs | 15 万次 × 128MB × 10s | 41,655 |
| 云函数资源使用量（死链检测） | 同上 | 20 万次 × 256MB × 2s | 11,104 |
| 云函数调用次数 | 13.3 点/万次 | 35 万次 | 465 |
| CDN 流量 | 210 点/GB | ~10 GB | ~2,100 |
| 云存储容量 | 4.54 点/GB/天 | ~1 GB | ~136 |
| **合计** | | | **~55,500 点** |

→ 个人版 40,000 点**不够**，超额 ~15,500 点 ≈ **¥15.5/月**。

### 1.3 100 用户的月度收支

| 项 | 金额 |
|---|---|
| 收入（¥12 × 100） | ¥1,200 |
| CloudBase 套餐（固定） | −¥19.9 |
| 资源点超额 | −¥0（见 §1.5，优化后 100 用户仍在 40,000 点套餐内） |
| MiMo API（满额；实际均值远低于此） | −¥24 |
| 支付手续费（微信 0.6%） | −¥7.2 |
| **净利** | **≈ ¥1,149（毛利率 96%）** |

### 1.4 两条关键结论

1. **固定成本 ¥19.9/月 → 2 个付费用户即回本。** 定价不需要用来"摊薄"固定成本。
2. **单个 Plus 用户的边际成本 ≈ ¥0.3**（AI ¥0.24 + 资源点 ¥0.05）。
   → **定价的约束不是成本，是支付意愿。**

### 1.5 超额到底影响多大（关键问题）

资源点用量与用户数近似**线性**（人均用量固定），所以：

| 付费用户数 | 资源点用量 | 超额 | 超额成本 | 占收入比 |
|---|---|---|---|---|
| 100 | ~34,400 点 | 无 | ¥0 | 0% |
| 200 | ~68,700 点 | 28,700 点 | ¥28.7 | **1.2%** |
| 1,000 | ~343,600 点 | 303,600 点 | ¥303.6 | **2.5%** |
| → 极限 | | | **¥0.34/用户/月** | **2.8%** |

**结论：超额的边际成本上限是 ¥0.34/用户/月，只占 ¥12 收入的 2.8%。**
它比 AI 成本（¥0.24）量级相当但绝对值极小，**完全不影响定价决策**。

**但这个结论是优化后才成立的。** mimo-chat 内存从 256MB 降到 128MB 之前：

| | 优化前（256MB） | 优化后（128MB） |
|---|---|---|
| 人均资源点 | ~557 点 | ~344 点 |
| 超额边际成本 | ¥0.56/用户/月（占收入 4.7%） | ¥0.34/用户/月（占 2.8%） |
| 100 用户是否超额 | **是**（超 ¥15.5） | **否** |

**结论：内存配置是控制超额的唯一有效杠杆**（资源点 ∝ 内存 × 时长），而它一次改动就抹掉了全部超额。

#### 尾部风险：超大书签库

人均线性假设会被极端用户打破。一个 10,000 书签的用户：

| | 每次自动扫描 | 每月（每周 1 次） | 占套餐 |
|---|---|---|---|
| 无规模上限 | 10,000 次外呼 | ~44,000 点 ≈ **¥44** | **击穿整个套餐** |
| 有上限（500） | 500 次外呼 | ~2,200 点 ≈ **¥2.2** | 5% |

已处理：迁移 `000007` 加 `linkcheck.auto.max = 500`，自动扫描超出部分本次不检查，
**并在 UI 上如实告知"另有 N 个超出单次上限未检查"**（不静默截断）。
手动检查不受此限（用户主动触发、有界）。

## 2. 定价建议

### 2.1 推荐方案：月付 ¥12 / 季付 ¥32 / 年付 ¥108

> 2026-10-31 校正：实际售价取 `plans` 表（`plus_monthly=1200`、`plus_yearly=10800`，落地页含 `pro_quarterly=3200`）。此前写的「年付 ¥99」从未落库，已按实际值更正。

| 方案 | 月付 | 年付 | 年付折算 | 评价 |
|---|---|---|---|---|
| **保守（已执行）** | **¥12** | **¥108** | ¥9/月（约 7.5 折） | 低于国际同类（LastPass ≈ ¥17/月）；2 个用户回本；转化阻力小；另有季付 ¥32/90 天 |
| 中性 | ¥15 | ¥118 | ¥9.83/月 | 更快回本，为将来切标准版（¥199）留余量 |
| 激进 | ¥19 | ¥148 | ¥12.33/月 | 需有明确差异化价值支撑 |
| ❌ 不建议 | < ¥9 | — | — | 价值感崩塌，年付折扣空间被压光 |

### 2.2 为什么选 ¥12 而不是更高

书签类工具的个人用户付费率本来就低（**1~5%**）。定价每上调 1 元，转化率的下降幅度往往大于收入增幅。¥12 是「不用犹豫」与「不显廉价」的平衡点。

### 2.3 为什么年付要主推

一次收款改善现金流；把续费流失降到最低（年付用户一年内不会因"忘了续费"流失）；年付金额约为月付的 9 倍时，年付用户占比每提高 10%，现金流改善是指数级的。

## 3. 免费版额度：当前缺一个"钩子"

现状 `free`（已按下方建议落地，见迁移 `20261025000006_free_tier_hooks.sql`）：storage 200MB / ai 50,000 token / history 90 天，并含死链检查 3 次/日、AI 请求 20 次/日、视频解析 1 次/日——免费档已有"钩子"，不再是空白。

> **2026-10-31 口径（额度执行已收口）**：`free` 实际落库为 storage 200MB / ai 50,000 token / ai.requests 20 次/日 / history 90 天 / linkcheck 3 次/日 / video.extract 1 次/日；`sync.devices` 因无设备体系**已从 plans 撤下**。**服务端已强制**：`ai.tokens.monthly`、`ai.requests.daily`、`video.extract.daily`、`video.deep.daily`、`linkcheck.daily`（手动检查，需登录 token）、`linkcheck.auto(.max)`、`history.days`（cleanup 保留期）。**仅展示未强制**：`storage.bytes`（购买页已标注"展示值，暂未限额"）。详见 `docs/QUOTA_ENFORCEMENT.md`。

> **2026-10-31 口径**：`video.deep`（口播 ASR + 画面 OCR）定位为**实验性实验室功能**（需浏览器扩展、仅桌面端，B站正式支持、抖音/小红书实验性），只给 PRO 2 次/日体验，不写入免费/PRO 的固定权益承诺，也不作为涨价依据。

建议（这些额度的成本都在噪声级别）：

| 项 | 现 free | 建议 free | plus |
|---|---|---|---|
| `storage.bytes` | 50MB | 200MB | 5GB |
| `ai.tokens.monthly` | 20,000 | 50,000 | 200,000 |
| `ai.requests.daily` | 无 | 20 | 100 |
| `linkcheck.daily` | 无 | 3 | 50 |
| `video.extract.daily` | 无 | 1 | 10 |
| `linkcheck.auto` | 无 | 无 | 1 |
| `history.days` | 30 | 90 | 90 |

理由：**让用户"用上了、想要更多"是唯一的转化路径。**
3 次/天的死链检测对资源点的影响是 0.5 点/天，等于没有。

## 4. 定价公布之后的策略（重要）

**定价一旦公布，几乎无法涨价。** 涨价会引发老用户反弹与投诉，而《用户服务协议》没有涨价条款，改价需要走变更公示流程。

成熟做法：

1. **靠加档提价，不靠涨价。** 现在定 ¥12 并永久保留；后续新增 Pro 档（¥29）承接重度用户。老用户价格永久锁定，并在协议中写明。
2. **早鸟名额**（建议，未执行）：前 100 名年付可给折扣，公开价按当前实测 **¥108/年**（历史上写的 ¥99 从未落库）。锁定感强，且利于口碑传播。
3. **别把价格定在"刚好够成本"的位置**：留出应对模型涨价（换 Pro 模型成本 ×3）与其他政策变化的余量。
4. **涨价幅度控制在 20% 以内且给老用户锁价**，超过这个幅度必须先做沟通。

## 7. 「真智能」架构下的成本与权益（2026-10-26 补充）

产品已全面转向真智能（概念本体 + 演化图谱 + 真模型动态生成），需重新审视成本与权益。

### 7.1 各能力的真实成本归属

| 能力 | 实现位置 | 成本 |
|---|---|---|
| 语义搜索 | 浏览器本地（概念本体 + 演化图谱） | **¥0** |
| 书签去重、分类兜底 | 浏览器本地（`ai-classify` / `bookmarkDedup`） | **¥0** |
| **添加书签时的智能预填** | **自动触发**：CF `/api/extract-metadata`（抓网页）→ MiMo 提炼标题/备注/分类；失败降级 `smartPrefill`（本地规则） | **≈ ¥0.002 / 次** |
| AI 对话 / AI 补齐 | CloudBase `mimo-chat`（用户主动） | MiMo + 资源点 |
| 意图寻站 / 平替（真模型） | CF Pages `/api/ai-candidates`（用户主动） | CF + MiMo |
| 死链海外探针 | CF Pages `/api/check-link`（自动，inconclusive 时） | CF + 出网 |

> ⚠️ **更正（2026-10-26）**：本文件初版把「URL 智能预填」列为纯本地零成本，**这是错的**。
> 实际链路：`useBookmark.ts` 的 `triggerAiFetch` 在新建书签时（500ms 防抖后）**自动**调用
> `fetchUrlMetadataAsync` → `/api/extract-metadata`，该端点在 CF 侧调 MiMo 做标题/备注提炼与
> 分类推荐（`max_tokens: 300`）。`smartPrefill.ts`（417 行纯本地规则引擎）是**降级兜底**，不是主路径。
>
> 单次成本 ≈ 输入 800~2,000 token（URL + 抓取到的标题/描述 + 候选分类列表）+ 输出 ≤300 token
> → **≈ ¥0.002**。
>
> **由此多出一个此前未计入的成本项：免费用户也在自动消耗。**
> 智能预填默认开启（`ui.smartFillEnabled = true`）且由输入 URL 自动触发，用户无感知。
> - 1,000 个免费用户 × 50 个书签/月 × ¥0.002 ≈ **¥100/月 纯支出**（无对应收入）
> - 控制手段：给免费档设 `ai.prefill.daily`（建议 20 次/天），超出直接走本地 `smartPrefill`
>   —— 零成本，标题/分类质量下降但仍可用，**体验损失远小于"功能不可用"**
>
> 结论仍成立但理由要更正：**成本没有暴涨，是因为单次成本极低（¥0.002）且本地有兜底**，
> 不是因为"完全没调模型"。

### 7.2 但新增了三个成本敞口

1. **批量操作会放大**：AI 补齐 100 个书签 = 100 次网页抓取 + 100 次模型提炼。
   单次输入可能上万 token（整页内容进模型）→ 批量是唯一需要按次数设闸的地方。
2. **死链海外探针**：境内判 inconclusive 时多一次外呼（跑在 CF，不吃 CloudBase 资源点，
   但吃 CF 函数调用与出网流量）。
3. **CF Pages 无法退役**：三条 `/api/*` 依赖它（见 `AI_BACKEND_SPLIT.md`），
   这意味着 CF 侧也要纳入成本监控。

### 7.3 权益分层要重划：按"是否真调模型"分，而不是按"功能新旧"分

**原则：真模型能力付费，本地智能能力免费。**

| 层级 | 内容 | 建议归属 |
|---|---|---|
| **基础智能**（¥0 或极低） | 语义搜索、去重、分类兜底（纯本地 ¥0）；URL 预填（真模型 ¥0.002/次，超限降级本地） | **免费**——这是"血液"，砍了产品就残废，用户能立刻感知；但预填要设日限，超出走本地引擎 |
| **重智能**（真调模型，单次成本高） | AI 对话、AI 补齐、意图寻站、批量整理 | **付费**，用次数/批量额度设闸 |

⚠️ **关键约束：不能用"砍 AI 能力"做免费版差异化。** 真智能一旦成为基础体验，
免费用户也能感知到差距，差异化的正确姿势是**额度与规模**（次数、批量大小、存储、设备数），
不是**能力有无**。

### 7.4 建议新增的额度键（等前端有消费逻辑时再落库，避免死键）

| 键 | free | plus | 闸的是什么 |
|---|---|---|---|
| `ai.prefill.daily` | 20 | 200 | **添加书签时的智能预填**（自动触发，默认开启；超出走本地引擎） |
| `ai.enrich.daily` | 2 | 20 | AI 补齐次数（网页抓取 + 模型提炼） |
| `ai.batch.monthly` | 0 | 5 | 批量整理次数（放大效应最强） |
| `ai.requests.daily` | 20 | 100 | AI 对话次数（已有，需按真智能场景重估） |

`ai.tokens.monthly` 的意义已经变了：本地智能不耗 token，
它现在只约束"真模型调用"，因此**次数类额度比 token 上限更好用也更好控**。

### 7.5 定价结论：¥12 仍成立

真智能没有推高成本（高频路径本地化），反而**增加了付费理由**：
用户能感知到 Plus 在"真模型能力"上的具体差异，而不是模糊的"更多额度"。

但影子计量的目标随之改变——从"测 token 分布"改为"**测真模型路径的单次成本**"：

```sql
-- 真实模型路径的单次成本（AI 补齐 / 寻站），比 token 总量更有指导意义
SELECT
  metric,
  count(*)                                    AS calls,
  round(avg(amount))                          AS avg_per_call,
  percentile_cont(0.5) WITHIN GROUP (ORDER BY amount) AS p50,
  percentile_cont(0.95) WITHIN GROUP (ORDER BY amount) AS p95
FROM public.usage_ledger
WHERE created_at > now() - interval '14 days'
  AND metric IN ('ai.requests', 'ai.chars')
GROUP BY metric;
```

有了这组数，就能反推 `ai.enrich.daily` / `ai.batch.monthly` 该给多少。
